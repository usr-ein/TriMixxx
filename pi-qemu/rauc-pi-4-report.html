TriMixxx A/B Updates

How the decks boot a locked system, take updates over the air with RAUC and the Pi's own tryboot, and fall back by themselves when an update goes wrong. Also how the emulated deck on your Mac mirrors the real one, so every update is rehearsed before a deck sees it.

  • Deckstrimixxx1, trimixxx2, more to come
  • Benchtrimixxx3, the spare Pi 4
  • Emulatedtrimixxx0, in pi-qemu
  • Full planpi-qemu/rauc-pi-4-setup.md

In one minute

  • Two copies of the system sit on every SD card: slot A and slot B. The deck runs one. An update writes only the other.
  • The Pi's firmware chooses the slot from a tiny file, autoboot.txt. A new slot is started once, on trial, with the firmware's one-shot tryboot flag.
  • A health check decides. If the new system can take the next update (it's on a network, by cable, home Wi-Fi or its own hotspot, and ssh runs), RAUC marks the new slot good and it becomes the default. If not, the next restart runs the old slot again, with nobody touching the deck. Anything else a release breaks, the next one fixes over the air.
  • The running system can't be changed. It's SquashFS, with a RAM layer on top that is gone at every restart. The deck's name and Wi-Fi live on a separate locked partition.
  • RAUC, the standard A/B updater packaged by Debian, does the installing. The emulated deck runs the same card and the same updates, so you rehearse on the Mac first.

1The card

Today a deck's card has two partitions, both writable. The new card has eight, each with one job.

  • p1 on its own: the file that picks the slot lives outside both slots, so installing a slot can never damage it. Raspberry Pi's own A/B example uses the same arrangement.
  • p7 data holds only what makes a deck itself: its name, its Wi-Fi and its ssh host keys. Updates never touch it, and it stays read-only until you unlock it with mount -o remount,rw /data.
  • p8 state is RAUC's own writable space: its install records, and the bundles you copy over.

2How a deck starts

There's no BIOS and no GRUB on a Pi. Its bootloader lives in a chip on the board and follows text files on the card. The A/B choice happens in the first two steps.

6The emulated deck and the real one

On a real deck, the Pi's firmware reads the card. On the Mac, pi-qemu reads the same card and plays the firmware's part, then hands QEMU the kernel. Below that line, both run the same software.

What only the bench deck can show

  • Whether a Pi 4's real start4.elf honours [boot_partition=N] (documented, still unverified on a Pi 4).
  • What the real bootloader does with a broken autoboot.txt, its version, and its settings.
  • Real watchdog timing, and an SD card losing power mid-write.

So trimixxx3 goes first. Its results set how pi-qemu emulates the firmware, not the other way round.

7How you work with it

Day to day, unchanged

pi-qemu deck up dev
pi-qemu deck deploy dev mixxx    # or config, system…

Make a release

git tag -m "TriMixxx 1.0.1" pi/v1.0.1
pi-qemu release build    # the tag's version: out/1.0.1/

Rehearse on the emulated A/B deck

pi-qemu release card trimixxx0 --version 1.0.0
pi-qemu deck up ab --from out/1.0.0/trimixxx0-1.0.0.img
pi-qemu deck ship ab --version 1.0.1
pi-qemu deck ssh ab rauc status

Ship to a deck, or roll back

pi-qemu deck ship --host trimixxx2 --version 1.0.1
# = the bundle over ssh, rauc install, reboot
ssh trimixxx2 sudo rauc status mark-active other
ssh trimixxx2 sudo reboot      # rollback: a trial of the old slot

A new deck needs one physical flash: pi-qemu release card trimixxx4 writes its name, Wi-Fi and ssh keys into that card's /data, and you flash it with Raspberry Pi Imager. Every later version arrives over the air.

8When something goes wrong

Every one of these is rehearsed on the emulated deck first, then on trimixxx3. All of them passed on the emulated deck on 2026-10-08, and on trimixxx3 the same day, power cut and watchdog included.

What goes wrongWhat catches itWhere the deck ends up
The bundle arrives damaged, or isn't yoursRAUC checks the signature before writing anythingstill on A
The power goes during the installOnly the idle slot was being writtenA
The power goes after the install, before the rebootThe trial flag doesn't survive a power-offA · install again
The new system doesn't boot (kernel panic, missing root)panic=10 restarts it, from the kernel or the initramfs; the flag is goneA
The new system freezesThe hardware watchdog, armed from the firmware on (kernel_watchdog_timeout), about 60 s into the hangA
It boots, but can't take the next update: no network, or no sshThe health check: mark-bad, then a restartA
It can take the next update, but Mixxx, the sound or the S3 failsNothing, on purpose: the next update fixes it over the airthe new slot
The power goes while committingThe one fragile moment: a few bytes on FAT. A copy goes to the state partition first, then the file, whole and synced. A broken autoboot.txt starts p2 (measured on trimixxx3); a check at start restores the copy, and returns to B if B was committedthe committed slot
A committed slot breaks later (SD corruption)Tryboot's one weak spot. Measured: the firmware's watchdog-partition setting doesn't switch slots. The bootloader's own watchdog does, before Linux starts: A starts after 45 s, and is committed if it passes the health check. A hang after Linux starts loops: put the card in a Mac and change the slot autoboot.txt commits (the volume BOOTSEL); the deck keeps that editA when B was committed; otherwise a hand on a Mac

9Standard parts and our own

Almost everything is either a standard component or a setting of one. The custom parts are few, small, and each exists for a stated reason.

JobWhat does itWhy we write any of it
Choose the slot, trial start, fall backPi firmware: autoboot.txt and trybootstandard—

Restart on hangs and panicsFirmware and systemd watchdogs, kernel panic=settings—

Build the card and the bundlegenimage, mksquashfs, rauc bundleconfig filesOne genimage.cfg, one Dockerfile, one manifest, driven by pi-qemu release build
Connect RAUC to the Pi firmwarerpi-tryboot, ~100 linesoursRAUC 1.13 has no Pi firmware backend yet. Adapted from Rtone's script, in production on dozens of devices. Deleted when RAUC's own (in review, aimed at 1.17) ships
Decide the deck is healthyA systemd unit that calls rauc status mark-goodoursRAUC's documented pattern; only its checks are ours: the deck is on a network, and sshd runs
Who this deck isOne small unit at startoursPicking per-deck app config (name, wiring, accent) has no standard tool
A/B in the emulatorpi-qemu's firmware step, one QEMU patchoursQEMU runs no Pi firmware; pi-qemu exists to be it

Why tryboot and not U-Boot: U-Boot would protect only the kernel and the system. It would write to the card at every boot, has no watchdog on the Pi, and adds boot time. Tryboot puts the firmware, device tree and config.txt under A/B too, and it's where Raspberry Pi, Ubuntu and RAUC itself are heading. The full comparison, with sources, is in the plan's appendix C.
