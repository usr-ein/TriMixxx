# TriMixxx 1.0.1

The deck's release after 1.0.0, made the same day (2026-10-15). It fixes the
deck's start: a state partition slow to appear no longer holds back the CPU's
full speed. For the DJ, the deck looks and plays as 1.0.0 does. On the Mac,
pi-qemu now sends to a real deck only over its cable, unless told to use the
Wi-Fi.

A bug-fix release: the Z of Sam's X.Y.Z (`pi-qemu/README.md`, "Cards and
releases").

## The deck

- **The CPU's full speed no longer waits for the state partition** (fb87203).
  In 1.0.0, `trimixxx-history.service`, which makes the History's directory
  on p8, held the boot's `multi-user.target` until p8 was mounted. A p8 slow
  to appear held it as long, and one whose label couldn't be read held it
  until its mount gave up, 90 s later. Only after that target does
  `cpu-governor.service` set the `performance` governor, which keeps
  scratching free of xruns. The unit is now off the boot's targets
  (`DefaultDependencies=no`), as Record set's has been since 1.0.0. The
  network, ssh and Mixxx never waited for it. A p8 that won't mount still
  leaves that power-up's History in RAM, as before.
- **Mixxx is 1.0.0's.** The fork's one commit since, usr-ein/mixxx@a98fc64,
  changes only how its Docker build on the Mac reads the sources (below). The
  code built is the same.

## Updating

- From 1.0.0 or from 0.1.1, the update is RAUC's bundle, as before:
  `pi-qemu deck ship --host ALIAS-eth --version 1.0.1`, over the deck's
  cable. The deck installs it into its other slot and starts it as a trial.
  Its health check keeps it once the network and ssh are up, or the deck
  goes back to what it ran.
- From 0.1.1, everything in 1.0.0's notes comes with it (its release, or
  `docs/releases/1.0.0.md`), and so does what they say about updating from
  0.1.1.
- The S3's firmware hasn't changed since 0.1.1: nothing to flash.
- The way back is Diagnostics' RESTART INTO, on 1.0.1: to whichever release
  the other slot holds. 0.1.1 has no such button: from it,
  `sudo rauc status mark-active other && sudo systemctl reboot` over ssh does
  the same.
- A new card is a deck's own, `pi-qemu release card DECK --version 1.0.1`,
  flashed from its `.img.xz`. The release's card, `trimixxx-1.0.1.img.xz`,
  holds no deck's identity: it starts as `trimixxx`, with no Wi-Fi and no
  ssh.

## Tried on emulated decks only

The fix to the History's unit was tried on emulated decks: a reboot, with the
unit active at 2.2 s and its directory made, and `multi-user.target` no longer
waiting for it. The cable check was tried on the Mac against test aliases,
over the Wi-Fi and over the dock's cable, and not yet against a real deck.

## Tooling, on the Mac

- **A real deck takes a deploy, an update or `deck prepare` only over a
  cable** (#43). With `--host`, `pi-qemu deck deploy`, `deck ship` and
  `deck prepare` first look at how the Mac reaches the deck, before they send
  anything. Ethernet and USB Ethernet pass. Wi-Fi is refused, and so is a
  route pi-qemu can't tell (a VPN's, a proxy's), unless `--wifi`. The refusal
  names the deck's cable alias, `ALIAS-eth`, which `pi-qemu deck alias`
  writes. An emulated deck is never checked. The docs' commands for a real
  deck now name its `-eth` alias.
- **Mixxx's Docker build bind-mounts the sources** (usr-ein/mixxx@a98fc64)
  rather than copying them in. A build no longer leaves a 0.56 GB layer of
  them in Docker's cache: one evening's builds had left 20, 11 GB.
- Docs: `mixxx_config`'s README says KEY SYNC's list shows nine rows, as it
  does (1b72b77); the crew's README, how long a reading of Docker's disk
  stands (87ced05); a comment in pi-qemu, why `worktree release`'s
  `--no-cache` build empties a tree (e65adb8); the release skill, that the
  tag GitHub makes for a release is checked (with these notes).
